# Cue 코드 리뷰 및 기능 제안 (v1.0.1 기준)

작성일 2026-08-04. 대상 커밋 `686a1f6`.

> **진행 상황.** 1.1 / 1.2 / 1.3 수정 완료(각 절 머리의 ✅ 참고). 이어서 T1-2(상대 날짜 + 지난 일정
> 강조)와 규모 회귀 테스트를 완료했다. **T2-5(수동 재정렬)는 제안 자체를 철회한다** — 사유는
> T2-5 절.

이 문서는 두 부분이다. 1부는 현재 코드의 실질적 지적사항, 2부는 사용자 니즈 관점의
기능·로직·UX 제안이다. 지적사항은 "고쳐야 할 것"이고, 제안은 "고르면 되는 것"이다.

## 0. 총평

31,000줄 규모에서 이 정도의 설계 일관성은 흔치 않다. 특히 다음은 그대로 유지할 가치가 있다.

- **파일이 진실 / SQLite는 버려도 되는 캐시**라는 단일 규칙이 실제로 코드에서 지켜진다.
  `IndexedTaskStore`가 유일한 쓰기 경로이고, 인덱스 스키마 변경이 마이그레이션 없이
  `PRAGMA user_version` 범프 + 재구축으로 끝난다.
- 실패 경로가 꼼꼼하다. 손상 파일 격리(`FileTaskStore.ReadRecordAsync`), 알 수 없는 타임존을
  `JsonException`으로 접어 시작 실패를 막는 처리(`ZonedDateTimeJsonConverter:49`),
  컨테이너 삭제 저널의 재개(`ResumeContainerDeletionsAsync`), 파서가 절대 throw하지 않는 규약.
- 반복 일정을 "회차 레코드(RecurrenceOccurrence)" 모델로 분리한 판단이 옳다. 완료 복사본을
  보관함에 흩뿌리는 흔한 설계보다 이력·상태 표현력이 크게 낫다.
- 주석이 "무엇을"이 아니라 "왜 이렇게 했는지"를 적는다. 유지보수 관점에서 가장 값비싼 종류의 주석이다.

아래 지적은 이 토대 위에서의 이야기다.

## 1부. 코드 리뷰

### 1.1 ✅ 문서와 구현이 어긋난 지점 (수정 완료)

**(a) 검색은 문서에만 있고 코드에 없다.**

`AGENTS.md`의 Architecture 절은 이렇게 단언한다.

> Read flow: every query (Today, Upcoming, by group, by tag, completed/incomplete filters,
> **title and notes search**) hits the SQLite index.

그러나 `Cue.Storage/Index/ITaskIndex.cs`의 25개 메서드 어디에도 검색 쿼리가 없고, UI에도 검색
진입점이 없다. 더 나아가 `SqliteTaskIndex`의 `tasks` 테이블 컬럼은
`id, title, group_id, checklist, when_kind, when_date, when_time, completed_at, deleted_at,
priority, sort_order, is_recurring`뿐이라 **`notes` 컬럼 자체가 존재하지 않는다.** 즉 노트 검색은
"쿼리를 하나 추가하면 되는 일"이 아니라 인덱스 스키마 변경이 필요하다.

→ 문서를 현재 상태(미구현)로 정정하거나, 2부 T1-1대로 구현하거나 둘 중 하나. 지금 상태는
문서를 믿고 들어온 사람(또는 AI 에이전트)이 "이미 있는 줄 알고" 잘못된 전제로 작업하게 만든다.

**(b) 우선순위 파싱도 문서에만 있다.**

`AGENTS.md` 첫 문단: "you type a single line, and it cues the next action, parsing the due date,
time, **and priority** out of plain text."

`Cue.Parsing` 전체에서 `Priority`는 한 번도 등장하지 않는다. 빠른 입력으로 중요도를 지정하는
경로는 없다. → 문서 정정 또는 T2-7 구현.

### 1.2 ✅ 성능: 알림 조정 루프가 매번 전체 폴더를 스캔한다 (수정 완료)

`Services/NotificationScheduler.cs:186-193`

```csharp
var tasks  = await _store.GetAllAsync<TaskItem>(cancellationToken);
var groups = await _store.GetAllAsync<TaskGroup>(cancellationToken);
```

`ITaskStore.GetAllAsync`는 `IndexedTaskStore`에서 **파일로 위임된다**(설계상 의도적으로 그렇다).
따라서 이 두 줄은 `tasks/` 폴더 전체를 열거하고 모든 JSON을 역직렬화한다.

이 조정 루프가 도는 시점은 두 가지다.

1. **모든 저장 이후** — `Changed` 이벤트 → 500ms 디바운스 → `ReconcileAsync`
   (`NotificationScheduler.cs:315-329`)
2. **15분마다** — `RunPeriodicAsync`

상세 패널은 자동저장이라 편집 한 번이 곧 저장 한 번이다. 할 일이 2,000개인 사용자는
제목 한 글자 고칠 때마다 2,000개 파일을 읽는다. 인덱스가 바로 옆에 있는데 쓰지 않는다.

**제안**: `ITaskIndex`에 알림 후보 전용 쿼리를 추가한다.

```sql
SELECT id, title, group_id, when_date, when_time, reminder
FROM tasks
WHERE deleted_at IS NULL AND completed_at IS NULL AND is_recurring = 0
  AND when_kind = 'OnDate' AND when_time IS NOT NULL
  AND when_date BETWEEN $today AND $today_plus_14
```

`reminder` 컬럼 추가가 전제인데, 인덱스는 언제든 재구축 가능하므로 `SchemaVersion`을 10으로
올리는 것으로 끝난다(마이그레이션 불필요 — 이게 이 아키텍처의 배당금이다).
그룹 이름도 `SelectRows`가 이미 하듯 LEFT JOIN으로 붙이면 두 번째 전체 스캔도 사라진다.

`BuildLiveTaskTags`도 같은 인덱스 쿼리(윈도우 조건만 제거)로 대체 가능하다.

### 1.3 ✅ 성능: 할 일 저장마다 참조 검증용 파일 읽기가 N+1번 발생한다 (수정 완료)

`Cue.Storage/IndexedTaskStore.cs:168-193` `NormalizeTaskReferencesAsync`

할 일을 저장할 때마다,

- `TaskGroupId`가 있으면 그룹 파일 1회 읽기
- `TagIds` 개수만큼 태그 파일 읽기

즉 태그 3개 달린 할 일의 자동저장 1회 = 파일 읽기 5회(본문 읽기 + 그룹 1 + 태그 3) + 쓰기 1회.

이 코드가 파일을 직접 읽는 이유는 명확하다. **Absent(없음)와 Unreadable(못 읽음)을 구분해야**
하기 때문이다(Unreadable은 보존, Absent만 제거). 인덱스는 이 구분을 못 한다.

하지만 한 방향은 인덱스로 확정할 수 있다. **인덱스에 살아 있는(`deleted_at IS NULL`) 그룹/태그로
잡히면 그 참조는 유효하다**가 확정이므로 파일을 읽을 필요가 없다. 인덱스에 없을 때만
기존 파일 경로로 폴백해서 Absent/Unreadable을 가리면 된다. 정상 케이스(거의 전부)에서 IO가
사라지고, 정책은 그대로다.

`GetTaskGroupsAsync`/`GetTagsAsync` 결과를 짧게 캐시하면 쿼리조차 대부분 생략된다.

### 1.4 성능: 태그 하나 삭제에 전체 할 일 파일을 읽는다

`IndexedTaskStore.cs:355` `DeleteTagAsync` → `ReadAllTasksForContainerMutationAsync`

전체 `tasks/` 폴더를 `ReadRequiredAsync`(손상 격리 없음)로 읽는다. "읽을 수 없는 자식이 있으면
작업을 완료로 선언하지 않는다"는 정책 때문에 의도적인 전체 스캔이다.

정책은 유지하면서 범위만 좁힐 수 있다. `task_tags` 인덱스로 대상 task id 집합을 먼저 뽑고,
**그 파일들만** required-read 하면 된다. 인덱스가 stale일 위험은 시작 시 전체 재구축이 있으니
실질적으로 낮다. 다만 이건 삭제라는 드문 동작이라 1.2/1.3보다 우선순위가 낮다.

### 1.5 신뢰성: 알림 예약이 "앱이 켜져 있을 때"만 일어난다

- 예약 창은 롤링 14일(`NotificationScheduler.RollingWindow`).
- 예약을 OS에 넣는 유일한 주체는 실행 중인 Cue다.
- **Windows 시작 시 자동 실행 옵션이 없다.** (`StartupTask`, 트레이 상주 코드 없음 — 전체 grep 0건)

따라서 3주 뒤 일정에 알림을 걸어둔 사용자가 그 사이 앱을 한 번도 열지 않으면, 알림은 OS에
등록되지 않고 **그냥 오지 않는다.** 리마인더 앱에서 이건 기능 갭이 아니라 신뢰성 결함에 가깝다.
사용자는 "가끔 알림이 안 온다"고 느끼고, 그 순간 앱을 신뢰하지 않게 된다.

가장 싼 해법은 T1-4(시작 프로그램 등록 + 트레이 최소화)다. 앱이 로그인 시 조용히 떠 있으면
14일 창은 사실상 항상 갱신된다.

### 1.6 UX 결함: 지난 일정(overdue)이 시각적으로 구분되지 않는다

`ViewModels/TaskRowViewModel.cs:331` `BuildSchedule`

```csharp
private static string Day(DateOnly d) => d.ToString("M월 d일 (ddd)", Korean);
```

모든 날짜가 절대 표기다. 그런데 오늘 뷰는 설계상 **지난 일정을 앞으로 굴려서 담는다**
(`ITaskIndex.GetTodayAsync`: "a When day today-or-earlier"). 결과적으로 오늘 목록 안에서
*오늘 마감*과 *2주 지난 항목*이 똑같은 회색 텍스트로 나란히 있다. 지난 항목 전용 색상 토큰도 없다
(`DesignTokens.xaml`에 overdue 계열 브러시 없음).

이건 코드 변경량 대비 사용자 체감이 가장 큰 항목이다. 2부 T1-2 참조.

### 1.7 접근성

`Controls/OmniInputBox.xaml`에 `AutomationProperties`가 **0건**이다. 앱의 정체성 그 자체인 입력
컨트롤인데 스크린 리더에 이름이 없다. 다른 화면은 상황이 낫다(`TaskListPage.xaml` 10건,
`WeeklyTimelinePage.xaml` 15건). 최소한 `AutomationProperties.Name`과, 파서가 인식한 토큰에 대한
`AutomationProperties.HelpText`(예: "내일 — 6월 30일 화요일로 인식됨")를 붙일 값어치가 있다.

### 1.8 되돌릴 수 없는 삭제

`RecordBase`는 소프트 삭제(`DeletedAt` 툼스톤)를 하고, `IndexedTaskStore.SaveCoreAsync:157`은
삭제된 레코드의 부활을 **명시적으로 거부한다.**

```csharp
if (existing?.IsDeleted == true && !record.IsDeleted)
    throw new InvalidOperationException($"A deleted {typeof(T).Name} cannot be restored through SaveAsync.");
```

즉 데이터는 디스크에 그대로 남아 있는데 앱 안에서 되살릴 방법이 없다. 실수로 지운 할 일은
사용자 입장에서 영구 삭제와 동일하다. 인프라의 절반(툼스톤)이 이미 있으므로 복구 경로 추가는
저렴하다. → T3-14.

### 1.9 자잘한 것들

- **`ReminderTiming.OneDayBefore`가 `TimeSpan.FromHours(24)`**
  (`Cue.Domain/ReminderTimeCalculator.cs:26`). DST 경계를 넘으면 "하루 전 같은 시각"이 아니라
  "정확히 24시간 전"이 된다. 한국 사용자에겐 무해하지만, 이 프로젝트가 타임존을 이렇게까지
  공들여 다루는 걸 생각하면 캘린더 연산(`ToLocal().AddDays(-1)`)이 의도에 더 맞다.
- **업데이트 자동 확인이 없다.** `UpdateService`는 완성도가 높지만(SHA-256 검증, 진행률,
  사일런트 설치 후 재실행), 호출은 설정 화면의 "업데이트 확인" 버튼뿐이다. 사용자는 설정에
  잘 안 들어간다. 시작 후 지연 확인 + 배지 정도면 충분하다.
- **키보드 조작이 컨트롤 단위에 머문다.** `KeyboardAccelerator`는 전체 코드베이스에 1건
  (`MainWindow.xaml.cs:1240`, 사이드바 Delete)뿐이고, 나머지는 개별 `KeyDown`의 Enter/Escape다.
  앱 레벨 단축키가 없어 마우스 없이는 사실상 운용이 안 된다. → T1-3.
- **테스트**: 파서/스토어/인덱스/반복/랭킹/알림 스케줄러까지 두텁고,
  `ViewModelRegressionTests`가 3,031줄로 뷰모델까지 덮는다. 좋다. 빠진 건 **규모 회귀 테스트**다.
  1.2·1.3의 문제는 정확성 테스트로는 절대 안 잡힌다. 할 일 5,000개 픽스처에서 저장 1회의
  파일 IO 횟수를 세는 테스트 하나면 재발을 막는다.

## 2부. 사용자 니즈 관점 제안

우선순위 근거는 "없어서 매일 아픈가"다.

### Tier 1 — 지금 없어서 매일 아픈 것

**T1-1. 검색 (Ctrl+F)**

할 일이 200개를 넘는 순간 필수가 된다. 지금은 어느 뷰에도 검색이 없어서, 두 달 전에 적어둔
할 일을 찾으려면 그룹을 하나씩 열어봐야 한다.

- 인덱스에 `notes` 컬럼 추가(스키마 버전 범프 → 재구축으로 자동 채워짐)
- `title LIKE`로 시작하고, 한국어 부분 일치가 아쉬우면 FTS5 trigram으로 승급
- UI는 별도 화면보다 **현재 목록 위의 필터 바**가 낫다. 그룹 안에서 좁히는 게 자연스럽다.

**T1-2. ✅ 상대 날짜 표기 + 지난 일정 강조 (완료)**

- `BuildSchedule`을 상대 표기로: `오늘`, `내일`, `어제`, `3일 지남`, 그 밖은 현행 절대 표기
- 지난 항목은 날짜 텍스트에 경고 톤(`CueOverdueBrush` 신설 — `CueDangerFillBrush` 재사용은
  삭제 액션과 의미가 겹치므로 피할 것)
- `TaskListItem`에 계산된 `IsOverdue`를 얹지 말고, 인덱스가 이미 today를 계산하므로
  `Map` 단계에서 `IsAheadOfSchedule`과 같은 방식으로 넣으면 된다

1.6에서 지적한 문제의 직접 해결. 변경량 대비 효과가 이 목록에서 가장 크다.

구현된 규칙: `오늘 / 내일 / 모레 / 어제 / N일 지남`(6일까지), 그 밖은 절대 날짜. 일주일 넘게 지난
항목은 "312일 지남"보다 날짜가 더 유용하므로 절대 표기로 돌아간다. **완료한 항목은 항상 절대
날짜**다 — 보관함은 이미 완료일로 묶어 보여주므로 완료된 일에 "5일 지남"을 붙이면 갚지 않은 빚처럼
읽힌다. `IsOverdue`는 미완료 + 과거 날짜일 때만 참이고, `CueOverdueBrush`(3개 테마 전부 정의, 고대비는
색이 아니라 문구로 전달)로 색을 입힌다.

색을 컨버터로 푼 대가가 하나 따라왔다. 컨버터가 돌려준 브러시는 변환 시점에 한 번 해석된
인스턴스이고, 바인딩이 그걸 로컬 값으로 얹어 스타일 setter(`{ThemeResource ...}`, 프레임워크가
테마 전환 때 재평가하던 쪽)를 덮는다. 테마를 바꿔도 `IsOverdue`는 그대로이니 컨버터는 다시 돌지
않는다. 비-overdue 분기도 테마 브러시를 돌려주므로 **날짜가 있는 모든 행**이 대상이다. 그래서
`TaskRowViewModel.RefreshThemedColors`(옛 `RefreshTagColors`)가 태그 칩과 일정 텍스트를 함께 다시
알리고, `TaskListPage`에 더해 `WeeklyTimelinePage`도 `ActualThemeChanged`를 구독한다 — 타임라인은
가상화로 카드를 다시 만드는 일이 없어(리사이즈는 제자리 재배치) 자기 교정이 아예 없던 쪽이다.

**T1-3. 앱 레벨 키보드 단축키**

최소 세트: `Ctrl+N`(빠른 입력 포커스) · `Ctrl+F`(검색) · `Ctrl+1~7`(뷰 전환) · `Ctrl+,`(설정) ·

"한 줄 입력이 핵심 매력"인 앱인데, 그 한 줄에 도달하려면 마우스를 잡아야 한다는 게 지금의
가장 큰 모순이다.

바로가기, MSIX는 `StartupTask` 매니페스트 확장으로 각각 처리하면 된다. 기본값은 꺼짐,
설정 > 알림 아래에 "Windows 시작 시 실행" 토글.

### Tier 2 — 계속 쓰게 만드는 것

**T2-5. ✗ 수동 순서 바꾸기 — 철회**

원래 진단은 "인프라가 90% 완성, 남은 건 UI 배선뿐"이었다. **그 진단이 틀렸다.** 착수해 보니
세 가지가 드러났고, 종합하면 이 기능은 넣지 않는 쪽이 맞다.

*첫째, 수동 정렬 모드 자체가 없었다.* `TaskSortMode`는 `Date`/`Name`/`Priority` 셋뿐이고 전부
**계산된 정렬**이라 `SortOrder`를 마지막 tiebreaker로만 쓴다. 즉 날짜순 목록에서 행을 옮겨도 다음
`LoadAsync`가 `OrderBy(WhenDate)`를 다시 적용하면서 그 이동을 덮어쓴다 — 순위는 저장되지만 화면에서는
제자리로 튕겨 돌아온다. 재정렬을 얹을 자리가 애초에 없었다.

*둘째, `Manual` 모드는 과거에 있다가 이미 제거된 적이 있다.* `AppPreferences.SortMode`의 주석이
"the removed \"Manual\" mode"를 명시적으로 언급하며(`06bedc8`), `EnumValue`가 파싱 실패 시 `Date`로
떨어지도록 방어까지 되어 있다. 즉 이건 미구현이 아니라 **한 번 내렸던 결정**이었다.

*셋째, 사이드바 재정렬도 실은 동작하지 않는다.* `ShellViewModel.ReorderTaskGroupCommand` /
`ReorderTagCommand`가 있지만 호출하는 코드가 없다(전체 grep 0건).

결론: 이 앱의 정렬은 "사용자가 배치를 관리한다"가 아니라 "날짜/이름/중요도 중 하나를 고르면 앱이
정렬해 준다"는 모델이다. 수동 배치를 되살리면 정렬 모드가 넷이 되고, 그중 하나에서만 재정렬이
동작하며, 나머지 셋에서는 같은 제스처가 조용히 무시되는 상태를 사용자가 학습해야 한다. 자연어 한 줄로
입력하면 앱이 알아서 정리해 준다는 제품의 전제와도 어긋난다. `SortOrder`/`FractionalRank`/
`IReorderService`는 그대로 남아 새 할 일의 추가 순서와 안정적 tiebreaker 역할을 계속한다.

**T2-6. 다중 선택 + 일괄 작업**

현재 `SelectionMode="None"`이라 선택 개념 자체가 없다. 태그 정리, 그룹 이동, 일괄 삭제, 일괄
날짜 변경이 전부 1건씩 반복 노동이다. Shift/Ctrl 클릭 + 하단 액션 바.

**T2-7. 빠른 입력에서 그룹/태그/중요도 지정**

`IQuickAddRule` 파이프라인이 "커스텀 규칙이 기본 규칙보다 먼저 돈다"로 설계돼 있어 규칙 추가만으로
확장된다. 다만 문법 선택은 신중해야 한다.

- `#그룹` `@태그` `!1` 기호 문법은 학습이 필요하고 한국어 문장에 이물감이 있다
- 대안: **입력 중 `/`를 치면 팔레트가 뜨는 방식**. 지금 있는 토큰 클릭 팝오버와 상호작용 언어가 같다
- 최소한 중요도(`!1`~`!4`)만이라도 먼저. 문서(1.1b)가 이미 있다고 주장하는 기능이기도 하다

**T2-8. 데일리 브리핑**

`NOTIFICATIONS.md`의 8단계로 계획돼 있으나 미구현(전체 grep 0건). 종일(`IsAllDay`) 작업은 현재
개별 알림이 없어서 **알림 사각지대**다. 설계 문서 스스로 "옵트인 데일리 브리핑이 커버한다"고
적어놨는데 그 커버가 아직 없다. 아침 8시에 "오늘 할 일 5개, 지난 일 2개" 토스트 하나면 된다.

### Tier 3 — 차별화

**T3-9. "밀린 일 한 번에 미루기"**

오늘 뷰가 지난 일정을 굴려 담는 구조라, 며칠 방치하면 오늘 뷰가 밀린 일로 가득 찬다. 이때
필요한 건 개별 날짜 수정 20번이 아니라 "안 한 일 전부 내일로" 버튼 하나다. T2-6(다중 선택)의
상위 사례이기도 하고, 이 앱의 오늘 뷰 설계와 가장 잘 맞는 기능이다.

**T3-10. 회고·통계**

`recurrence_occurrences` 테이블이 이미 회차별 완료/누락 이력을 갖고 있고, `completed_at`으로
날짜별 집계가 된다. 주간 완료 수, 그룹별 분포, 반복 일정 달성률 정도는 새 데이터 수집 없이
쿼리만으로 나온다. 습관 추적 앱과 겹치는 지점이라 차별화 가치가 있다.

**T3-11. 데이터 접근성 — 내보내기 / 폴더 열기 / 백업**

"파일이 진실"이라는 아키텍처는 사용자에게도 팔 수 있는 가치인데 지금은 노출이 없다.

- 설정 > 정보에 **"데이터 폴더 열기"** 버튼 (한 줄짜리 `Process.Start`)
- Markdown / CSV 내보내기
- 데이터 폴더 경로 변경 UI (`FileTaskStoreOptions.RootPath`가 이미 설정값이다)

**T3-12. 클라우드 폴더 동기화**

로드맵의 최종 목표이고 준비는 끝나 있다(레코드 단위 파일, 툼스톤, UTC+타임존 보존,
`IndexPath` 분리). 시작할 때의 검토 지점은 `AGENTS.md`가 이미 지목해 둔
`NormalizeTaskReferencesAsync`의 Absent 분기다 — 동기화 중에는 "아직 안 온 파일"이 Absent로
보이고, 지금 정책은 그걸 참조 제거로 처리한다. 그대로 두면 동기화 중 태그가 사라진다.

### UX 디테일

**T3-13. 첫 실행 온보딩**

빈 상태가 `"여기에 표시할 할 일이 없어요."` 한 줄뿐이다(`TaskListPage.xaml:659`). 이 앱의 핵심
매력은 파서인데, 새 사용자는 **뭘 칠 수 있는지 모른 채** 빈 화면을 본다. README에 있는 예시
5줄이 그대로 온보딩 카피다.

> "내일 오후 3시 회의 준비" 라고 그냥 적어보세요

첫 실행 시 예시 3개를 클릭 가능한 칩으로 보여주고, 누르면 입력창에 채워지는 정도면 충분하다.

**T3-14. 휴지통 (삭제 취소)**

1.8 참조. 소프트 삭제 인프라는 이미 있고 복구 경로만 없다. 필요한 건
`ITaskStore.RestoreAsync`(또는 `SaveCoreAsync`의 부활 금지 규칙을 우회하는 전용 경로) +
"최근 삭제" 뷰. 최소 버전은 삭제 직후 스낵바 되돌리기만으로도 사고의 90%를 막는다.

**T3-15. 앱 안에서의 미루기(스누즈)**

토스트 스누즈는 OS에 위임했지만(옳은 판단), 앱 안에는 미루기가 없다. 행 우클릭 →
"내일로 / 다음 주로 / 날짜 선택"이 목록에서 가장 자주 쓰이는 동작 중 하나다.
