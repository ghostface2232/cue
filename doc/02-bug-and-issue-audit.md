## 요약

빌드와 626개 테스트는 모두 통과했고 알려진 취약 NuGet 패키지도 발견되지 않았다. 따라서 현재 확인된 P0(즉시 배포 중단) 실패는 없다. 다만 다음 릴리스 전에 고치는 편이 좋은 P1 문제가 6개 있다.

1. 날짜 문구만 입력하거나 주간 타임라인에서 빈 작업을 만들면 **제목 없는 레코드가 영구 저장될 수 있음**.
2. GitHub 자동 업데이트가 체크섬이 없는 릴리스를 **검증 없이 허용하는 fail-open 경로**를 가짐.
3. 알림 본문 클릭이 앱만 열고 **해당 작업으로 이동하지 않음**.
4. 빠른 추가·설정 탐색·콤보박스의 접근 가능한 이름이 비고, 작업 행 키보드 동작이 삭제에만 한정됨.
5. 첫 실행 창의 물리 픽셀 크기와 NavigationView의 DIP 임계값이 충돌해 고배율에서 핵심 탐색이 숨음.
6. 가상화 요소가 실현될 때마다 진입·퇴장 모션이 반복되고, 일부 사이드바 모션은 Windows의 애니메이션 끄기 설정을 따르지 않음.

## P1-01. 제목 없는 TaskItem이 저장될 수 있음

### 근거와 재현 경로

빠른 추가는 원문이 공백인지 먼저 검사하지만(`ViewModels/TaskListViewModel.cs:360-366`), 파서가 날짜 문구를 제거한 뒤의 `parsed.Title`은 다시 검사하지 않고 그대로 저장한다(`ViewModels/TaskListViewModel.cs:387-424`). 따라서 `내일`, `오늘 3시`, `매주 월요일`처럼 일정 토큰만 입력하면 빈 제목 작업이 만들어질 수 있다.

추가 경로도 같은 상태를 허용한다.

- 상세 패널은 제목을 `Trim()`한 뒤(`ViewModels/TaskDetailViewModel.cs:671-678`) 빈 값 검증 없이 레코드에 대입한다(`ViewModels/TaskDetailViewModel.cs:751-759`).
- 주간 타임라인의 빈 영역 더블클릭은 빈 `TaskItem`을 즉시 저장하고 상세를 연다(`ViewModels/WeeklyTimelineViewModel.cs:154-174`). 사용자가 제목을 적지 않고 닫으면 빈 레코드가 남는다.
- 체크리스트 제목도 공백을 저장할 수 있으나 부모 작업보다 영향은 낮다.

### 영향

제목이 없는 행은 식별·검색·복구하기 어렵고, 비어 있는 화면처럼 보이거나 접근성 트리에서 의미 없는 항목이 된다. 세 생성/편집 경로가 서로 다른 정책을 가지므로 이후 검색과 동기화에도 불량 데이터가 전파된다.

### 수정 방향

- `TaskItem` 도메인에 UI 검증을 넣기보다, 모든 생성/편집 use-case가 공유하는 제목 정책을 둔다.
- 빠른 추가는 파싱 후 제목이 비면 저장하지 말고 `할 일 내용을 입력해 주세요` 인라인 오류를 표시한다. 날짜 토큰은 입력창에 유지한다.
- 타임라인 빈 공간 추가는 임시 draft UI만 열고, 유효한 제목이 생길 때 최초 저장한다. 또는 닫을 때 빈 신규 레코드를 tombstone 처리한다.
- 상세 패널에서 기존 제목을 전부 지우면 저장을 막고 이전 값으로 복원하거나 명시적 오류 상태를 보여 준다.
- 제목 최대 길이와 공백 정규화도 같은 정책에서 처리한다.

### 완료 조건

- `내일`, `매주 월요일`, 공백, 날짜+시간만 입력하는 빠른 추가가 파일을 만들지 않는다.
- 기존 작업 제목을 공백으로 바꿔도 JSON에 빈 제목이 저장되지 않는다.
- 타임라인에서 빈 새 작업을 열었다가 닫아도 활성 레코드·인덱스 행이 남지 않는다.
- 세 경로와 앱 재시작 후 상태를 테스트한다.

## P1-02. 자동 업데이트 무결성 검증이 fail-open임

### 근거

`UpdateCheckResult.Sha256Url`은 이전 릴리스에 체크섬이 없으면 null을 허용하고(`Services/UpdateService.cs:15-23`), 다운로드 후 URL이 있을 때만 검증한다(`Services/UpdateService.cs:221-222`). 그 뒤 설치 파일은 silent installer로 실행된다(`Services/UpdateService.cs:319-348`). 공개 릴리스 중 `v0.1.0`~`v0.1.3`은 체크섬 자산이 없고, 최신 `v1.0.1`은 설치 파일과 체크섬을 함께 제공한다.

현재 최신 릴리스는 검증되므로 즉시 악용이 확인된 P0은 아니다. 그러나 향후 릴리스에서 체크섬 업로드가 누락되면 자동 업데이트가 검증 없이 실행되는 구조다. 또한 설치 파일과 체크섬이 같은 GitHub 릴리스에 있어 체크섬은 전송 오류 탐지에는 유용하지만 게시자 신뢰를 독립적으로 증명하지는 못한다.

### 수정 방향

1. 체크섬 자산이 없으면 `UpdateAvailable=false` 또는 명시적 “검증할 수 없는 업데이트” 오류로 처리한다.
2. 다운로드 크기, SHA-256, 파일 이름을 모두 확인한 뒤에만 실행한다.
3. GitHub 배포용 Inno Setup 실행 파일에 Authenticode 서명을 적용하고 실행 전 서명 주체를 검증한다.
4. 릴리스 워크플로에서 installer와 `.sha256`이 모두 없으면 publish를 실패시킨다.
5. MSIX 채널은 Microsoft Store 서명을 신뢰하므로 이 경로와 분리된 현재 설계를 유지한다.

### 완료 조건

- 체크섬 누락·불일치·형식 오류·다운로드 변조 시 파일이 삭제되고 실행되지 않는다.
- 서명되지 않았거나 기대한 publisher가 아닌 설치 파일은 실행되지 않는다.
- 성공/실패 경로가 단위 테스트와 릴리스 스모크에 포함된다.

## P1-03. 알림 본문 클릭이 작업 상세로 이동하지 않음

### 근거

알림 문서는 본문 클릭 시 앱 활성화 후 해당 작업으로 이동한다고 명시한다(`NOTIFICATIONS.md:34`). 실제 활성화 코드는 창을 전면으로 가져온 뒤 `TaskId`를 버리며 TODO를 남겨 둔다(`App.xaml.cs:144-153`). 완료 액션 처리와 달리 일반 본문 클릭은 사용자 맥락을 복원하지 못한다.

### 수정 방향

- Shell에 `NavigateToTaskAsync(Guid taskId)`라는 안정적인 진입점을 만든다.
- 활성 작업이 Today/Upcoming/완료 보기 중 어디에 있든 상세 패널을 열 수 있게 하고, tombstone/누락/손상 레코드는 한국어 오류로 안전하게 처리한다.
- cold start, 이미 실행 중, 다른 가상 데스크톱, 완료된 작업, 반복 시리즈를 각각 검사한다.

### 완료 조건

- 알림 본문 클릭 한 번으로 해당 작업 상세와 올바른 목록 맥락이 열린다.
- 존재하지 않는 ID는 앱을 크래시시키지 않고 Today 또는 기본 화면으로 폴백한다.
- 문서와 구현이 동일한 동작을 설명한다.

## P1-04. 접근성 이름·키보드 조작·터치 목표가 불완전함

### 실행 검사 결과

WinApp UI Automation으로 실제 실행 앱을 검사했을 때 다음 컨트롤의 `Name`이 비어 있었다.

- 빠른 추가 `RichEditBox`: `Controls/OmniInputBox.xaml:19-48`.
- 설정 섹션의 아이콘형 `ListViewItem` 5개: `Pages/SettingsPage.xaml:263-314`.
- 한 주 시작 요일, 시간대 `ComboBox`: `Pages/SettingsPage.xaml:359-390`.

작업 행과 타임라인 카드는 포커스 가능하지만 `KeyDown`에서 Delete만 처리한다(`Pages/TaskListPage.xaml.cs:236-245`, `Pages/WeeklyTimelinePage.xaml.cs:377-386`). 완료 체크박스 스타일은 최소 크기를 0으로 두고 20px 원형 시각 요소 중심으로 구성돼(`Styles/DesignTokens.xaml:500-513`) 고빈도 목표가 약 24px에 머문다. 체크리스트 삭제 32px, 사이드바 추가 26px 등도 터치·저시력 사용자에게 작다.

| Before | After |
| --- | --- |
| 스크린 리더가 빠른 추가와 설정 아이콘을 이름 없이 읽음 | `AutomationProperties.Name` 또는 `LabeledBy`로 목적과 현재 상태를 읽음 |
| 포커스된 행에서 Delete만 동작 | `Enter` 상세, `Space` 완료, 방향키 이동, Delete 삭제 |
| 20~32px 시각 크기가 클릭 영역이기도 함 | 시각 크기는 유지하되 투명 hit box를 최소 40×40 DIP로 확장 |
| 아이콘 툴팁이 접근 가능한 이름 역할까지 암묵적으로 담당 | 툴팁, 접근 가능한 이름, 도움말을 각각 명시 |

### 완료 조건

- Accessibility Insights 또는 UI Automation에서 모든 핵심 입력·탐색·행 액션의 Name/Role/State가 비어 있지 않다.
- 키보드만으로 빠른 추가, 목록 이동, 상세, 완료, 삭제 확인, 설정 변경을 수행한다.
- 200% 배율과 Windows 고대비/모션 끄기에서 포커스 시각화가 분명하다.
- 시각적 원의 크기를 키우지 않고도 포인터 hit target이 최소 40×40 DIP다.

## P1-05. 고배율 첫 실행에서 사이드바가 숨음

### 근거

창 기본 크기는 900×640 물리 픽셀로 설정된다(`MainWindow.xaml.cs:22-23`, `MainWindow.xaml.cs:211-212`). NavigationView 임계값은 880/640 DIP다(`MainWindow.xaml:50-51`). 150% 배율에서는 같은 물리 크기가 약 600 DIP가 되어 pane이 overlay/hidden 상태로 시작한다. 실제 150% 환경의 첫 실행에서 사이드바가 닫힌 상태를 확인했다.

### 영향

첫 실행 사용자가 그룹·태그·Today·설정을 한눈에 보지 못하고, 앱이 큰 빈 문서처럼 보인다. `앞으로`와 `언젠가`까지 기본 숨김이라 정보 구조의 학습 비용이 더 커진다.

### 수정 방향

- 저장된 창 위치가 없는 경우 기본 크기를 현재 모니터 DPI 기준 DIP→physical pixel로 변환한다.
- 또는 NavigationView 임계값을 실제 최소 레이아웃과 함께 다시 측정한다.
- 화면 work area를 넘지 않도록 clamp하고 100/125/150/200% 매트릭스를 스모크 테스트한다.

### 완료 조건

- 지원 배율에서 첫 실행 시 사이드바와 빠른 추가가 동시에 보인다.
- 작은 화면에서는 의도적으로 Compact가 되며 햄버거 버튼과 pane 상태가 명확하다.
- 기존 사용자의 저장된 창 위치·크기는 그대로 복원된다.

## P1-06. 가상화 재활용 모션과 모션 감소 설정 누락

### 모션 감사표

| 우선순위 | 문제 | 근거 | 권장 수정 |
| --- | --- | --- | --- |
| P1 | 목록의 `ItemsRepeater.ElementPrepared`마다 fade+scale+stagger가 재실행됨 | `Pages/TaskListPage.xaml.cs:938-961` | 가상화 실현/재활용에서는 모션 제거. 사용자 명시적 추가·완료·삭제에만 피드백 |
| P1 | `ElementClearing`에서도 fade를 시작해 스크롤 재활용과 실제 제거를 구분하지 못함 | `Pages/TaskListPage.xaml.cs:964-986` | 실제 컬렉션 변경 이벤트에서만 퇴장 모션, recycling은 즉시 초기화 |
| P1 | 주간 타임라인 행도 실현될 때마다 fade+scale+stagger | `Pages/WeeklyTimelinePage.xaml.cs:623-646` | 최초 보기 전환 또는 명시적 삽입에만 제한하고 스크롤에는 적용하지 않음 |
| P1 | 사이드바 섹션 slide/fade가 `UISettings.AnimationsEnabled`를 확인하지 않음 | `MainWindow.xaml.cs:879-918` | Windows 모션 끄기 시 translation 제거·즉시 상태 변경, opacity만 필요한 경우 짧게 유지 |
| P2 | 빠른 토글에 keyframe과 단일 collapse timer를 사용 | `MainWindow.xaml.cs:895-924` | 반복 입력 시 현재 상태에서 retarget하거나 즉시 종료; 중간 상태가 남지 않게 테스트 |

긍정적인 점도 있다. 목록·타임라인 페이지는 `UISettings().AnimationsEnabled`를 읽고(`Pages/TaskListPage.xaml.cs:48`, `Pages/WeeklyTimelinePage.xaml.cs:40`), 애니메이션 속성도 주로 GPU 친화적인 opacity/scale이며 300ms 이하다. 문제는 속도보다 **빈도와 트리거 위치**다. 가상화 실현은 사용자가 의미 있는 상태 변화를 요청한 사건이 아니며 스크롤 중 수십 번 발생할 수 있다.

| Before | After |
| --- | --- |
| 스크롤로 재실현된 행이 매번 살짝 나타나고 커짐 | 스크롤은 완전히 안정적이고 즉시 표시 |
| 모션 끄기에서도 사이드바 항목이 위아래로 이동 | 위치 이동 없이 즉시 상태 변경, 필요한 상태 구분만 opacity로 표시 |
| 재활용과 실제 삭제가 같은 퇴장 효과를 공유 | 완료·삭제 같은 의미 있는 사건만 짧은 피드백 |

### 판정

**Block — 현재 목록/타임라인의 모션 확장은 보류한다.** 위 P1 두 종류, 즉 가상화 재활용 애니메이션 제거와 MainWindow의 모션 감소 준수를 먼저 고쳐야 한다. 이후에도 키보드로 반복되는 행 이동·검색·팔레트 토글에는 진입/퇴장 애니메이션을 추가하지 않는다.

### 완료 조건

- 긴 목록을 위아래로 스크롤해도 재활용된 행에 진입 모션이 재생되지 않는다.
- Windows `Animation effects`를 끄면 translation/scale 기반 이동이 실행되지 않는다.
- 빠른 섹션 토글을 반복해도 opacity/translation/IsExpanded가 중간 상태에 남지 않는다.
- 10,000개 scale 테스트에서 스크롤 프레임 안정성이 기존보다 나빠지지 않는다.

## P2-01. 그룹·태그 이름 중복과 공백 정규화 정책이 없음

생성/이름 변경 경로는 주로 공백 여부만 검사한다. 대소문자, 앞뒤 공백, Unicode 정규화 기준이 없으면 시각적으로 같은 그룹·태그가 여러 개 생겨 탐색과 빠른 분류가 모호해진다.

### 권장 수정

- 표시 이름은 원래 표기를 보존하되 비교 키는 trim + Unicode normalization + culture-aware/case-insensitive 규칙으로 고정한다.
- 중복을 금지할지 허용 후 구분할지 제품 결정을 문서화한다. Cue의 1단계 그룹 구조에서는 금지가 더 단순하다.
- 생성, rename, 상세 패널 태그 생성, sync 병합의 같은 정책을 쓴다.

## P2-02. “Markdown 메모” 명세와 실제 편집기가 불일치

`AGENTS.md:121`은 Markdown notes라고 설명하지만 목록과 주간 상세 패널은 plain multiline `TextBox`만 제공한다(`Pages/TaskListPage.xaml:784`, `Pages/WeeklyTimelinePage.xaml:489`). 저장 형식으로 Markdown 문자열을 허용한다는 뜻이라면 문구를 “메모”로 고쳐야 하고, 사용자 기능이라면 최소한 링크·체크박스·미리보기 규칙이 필요하다.

### 권장 결정

- foundation에서는 문구를 “일반 텍스트 메모(원문은 Markdown 호환)”로 낮추는 편이 안전하다.
- Markdown 렌더링을 출시한다면 편집/미리보기 전환, 링크 보안, 테마, 접근성, export의 동일 렌더링을 함께 정의한다.

## P2-03. 상세 패널 중복이 회귀 가능성을 높임

메모·체크리스트·반복 이력·닫기/flush 동작이 목록 페이지와 주간 페이지에 중복된다. 최신 테마 수정 커밋 `dac39ce`, `4a6945d`가 양쪽을 함께 고친 것은 이미 변경 비용의 증거다. 당장 사용자에게 보이는 단일 버그라기보다 테마·접근성·저장 상태가 한 화면에서만 고쳐질 위험이다.

수정 방향과 완료 조건은 `doc/01-improvement-roadmap.md`의 “상세 패널을 공용 컴포넌트로 추출”을 따른다.

## P2-04. 알림 문서의 현재/미래 기능 경계가 흐림

`NOTIFICATIONS.md:9`은 종일 작업을 일일 브리핑이 다룬다고 현재형으로 읽히지만, `NOTIFICATIONS.md:48`은 이를 후속 phase로 둔다. 구현 전까지는 “계획됨/현재 미지원”을 명시해 테스트·지원 대응의 기준을 맞춰야 한다.

## 수정 권장 순서

1. **제목 불변식**을 먼저 고쳐 새 불량 레코드 생성을 차단한다.
2. **업데이터 fail-closed**와 서명 정책을 다음 배포 전에 확정한다.

7. 공용 상세 패널을 추출한 뒤 UI 자동화 스모크를 CI에 올린다.
